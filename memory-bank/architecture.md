# 架构说明

## 当前阶段

项目已完成第 3 步：定义基础牌数据模型。

当前工程是一个浏览器端本地运行的 Vite + TypeScript + 原生 HTML/CSS 应用。项目已拆分出游戏状态模块、基础牌数据模型、界面渲染模块和事件绑定模块，但仍不包含牌池生成、洗牌、玩家状态、计分、AI、胡牌判断或正式界面交互逻辑。

## 根目录文件

### `package.json`

项目 npm 配置文件，声明当前工程为私有前端项目，并配置基础脚本：

- `dev`：启动 Vite 开发服务器。
- `build`：先执行 TypeScript 类型检查，再执行 Vite 生产构建。
- `test`：运行 Vitest 单元测试。

当前开发依赖包括：

- `vite`：前端开发服务器与构建工具。
- `typescript`：类型检查与 TypeScript 支持。
- `vitest`：单元测试框架。

### `package-lock.json`

npm 依赖锁文件，用于固定依赖解析结果，保证后续开发者安装到一致的依赖版本。

### `index.html`

浏览器入口 HTML 文件。

职责：

- 提供页面基础结构。
- 挂载根节点 `#app`。
- 通过 `<script type="module" src="/src/main.ts">` 加载 TypeScript 入口。

### `tsconfig.json`

TypeScript 配置文件。

职责：

- 启用严格类型检查。
- 使用浏览器 DOM 类型。
- 使用适合 Vite 的 ES 模块与 Bundler 模块解析配置。
- 当前不输出编译产物，构建产物由 Vite 负责生成。

### `vite.config.ts`

Vite 配置文件。

职责：

- 提供 Vite 默认构建与开发服务器配置入口。
- 配置 Vitest 的基础测试环境。
- 当前不引入 React、Vue 或其他前端框架插件。

## `src/` 目录

### `src/main.ts`

当前应用入口文件。

职责：

- 引入全局样式。
- 调用 `createInitialGameState()` 创建初始化状态。
- 查找 `index.html` 中的 `#app` 根节点。
- 调用 `renderApp()` 完成页面渲染。
- 调用 `bindAppEvents()` 建立事件绑定入口。

当前限制：

- 不包含任何麻将规则逻辑。
- 不包含牌山、玩家、计分、AI、胡牌判断或回合状态。
- 后续仍应保持入口职责轻量，只负责初始化和连接模块。

### `src/game/` 目录

游戏核心逻辑目录。

职责：

- 承载牌定义、牌山、玩家状态、对局状态、规则判断、计分和电脑行动等核心逻辑。
- 核心逻辑不得依赖 DOM 或界面渲染实现。

当前限制：

- 目前包含最小初始化状态模块和基础牌数据模型。
- 尚未实现牌池生成、洗牌、发牌、摸打、胡牌、计分或 AI。

### `src/game/game-state.ts`

当前最小游戏状态模块。

职责：

- 定义 `GameStatus`，目前仅包含 `not-started`。
- 定义 `GameState`，目前包含初始化页面所需的 `status`、`title` 和 `subtitle`。
- 提供 `createInitialGameState()`，用于创建当前初始化状态。

当前限制：

- 只是第 2 步的结构占位状态，不是完整对局状态。
- 后续第 8 步实现完整对局状态时，应在此基础上扩展或重构，但仍需保持与 UI 解耦。

### `src/game/tile.ts`

基础牌数据模型模块。

职责：

- 定义本项目允许使用的牌类型：索子与三元牌。
- 定义 `SouzuRank`，限制索子只能是一索至九索。
- 定义 `DragonValue`，限制字牌只能是白、发、中。
- 定义 `SouzuTile`、`DragonTile` 和联合类型 `Tile`。
- 导出 `allowedTiles`，作为当前项目唯一允许牌种列表。
- 导出 `tileIds`，提供稳定的牌 ID 列表。
- 导出 `compareTiles()`，用于手牌、测试和后续规则中的确定性排序。
- 导出 `isSameTile()`，用于按稳定 ID 判断两张牌是否为同一种牌。
- 导出 `getTileById()`，用于根据牌 ID 获取对应牌定义。

当前牌 ID 约定：

- 索子使用 `souzu-1` 至 `souzu-9`。
- 三元牌使用 `dragon-white`、`dragon-green`、`dragon-red`。

当前显示顺序：

- 一索至九索。
- 白、发、中。

当前限制：

- 不包含万子、筒子、东南西北风牌或赤宝牌。
- 只定义牌种，不生成四张实体牌，也不负责洗牌。
- 第 4 步生成完整牌池时应复用 `allowedTiles`，不要重复定义允许牌种。

### `src/game/tile.test.ts`

基础牌数据模型测试文件。

职责：

- 验证允许牌种数量正好为 12。
- 验证允许牌种包含一索至九索、白、发、中。
- 验证不会包含万子、筒子、风牌或赤宝牌。
- 验证同一种牌的比较结果稳定。
- 验证排序后索子按一至九排列，字牌按白、发、中排列。

当前限制：

- 只覆盖牌种定义和排序规则。
- 尚未覆盖完整牌池生成、每种牌四张、洗牌或发牌逻辑。

### `src/ui/` 目录

界面层目录。

职责：

- 后续承载页面渲染、用户输入事件和 DOM 交互连接逻辑。
- 只读取或传递游戏状态，不应直接实现核心麻将规则。

当前限制：

- 当前只包含初始化页面渲染和事件绑定占位。
- 尚未实现正式游戏布局、手牌点击、胡牌按钮或新对局按钮。

### `src/ui/render.ts`

页面渲染模块。

职责：

- 导出 `renderApp(container, state)`。
- 根据 `GameState` 渲染当前初始化页面。
- 将 DOM 生成逻辑从 `src/main.ts` 中拆出。

当前限制：

- 只渲染标题、说明文案和当前状态标记。
- 后续正式界面应继续让渲染层只负责展示，不直接修改规则状态。

### `src/ui/events.ts`

事件绑定模块。

职责：

- 导出 `bindAppEvents(container)`，作为后续用户操作事件的统一入口。
- 当前返回一个空的清理函数，表示暂未绑定实际事件。

当前限制：

- 尚未绑定任何玩家操作。
- 后续实现打牌、胡牌、新对局等交互时，应在此连接 UI 事件与游戏流程模块。

### `src/styles.css`

当前全局样式文件。

职责：

- 设置页面基础字体、背景和排版。
- 为初始化占位页面提供居中展示样式。

当前限制：

- 只服务最小占位页面。
- 尚未定义正式游戏界面布局。

### `src/main.test.ts`

基础测试文件。

职责：

- 验证入口导出的 `initialGameState` 符合当前初始化状态。
- 验证 `renderApp()` 可以根据初始化状态渲染标题、说明文案和状态标记。

当前限制：

- 只覆盖模块化初始化和基础渲染。
- 尚未覆盖任何正式游戏规则或界面交互。

## 后续架构方向

第 4 步应在 `src/game/` 下实现完整牌池生成，建议新增独立的牌池或牌山模块，例如 `src/game/deck.ts`。

后续新增规则逻辑时，应继续遵守以下约束：

- `src/main.ts` 只负责初始化和连接模块。
- `src/game/` 不依赖 DOM，不直接处理页面事件。
- `src/ui/` 不实现麻将规则，只负责展示状态和转发用户操作。
- 第 4 步生成完整牌池时应复用 `src/game/tile.ts` 的 `allowedTiles`。
- 每个基础模块都应配套测试，避免形成单体巨文件。
